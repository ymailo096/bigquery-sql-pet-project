# BigQuery SQL Pet Project: Logistics Data Warehouse

Цей проєкт демонструє трансформацію сирих денормалізованих логістичних даних із пласких файлів у нормалізоване сховище даних (Data Warehouse) у Google BigQuery за архітектурою «Зірка» (Star Schema), а також автоматизацію очищення та перевірку цілісності даних за допомогою SQL.

## 🛠️ Технологічний стек
* **Сховище даних:** Google BigQuery (Sandbox Environment)
* **Джерело даних:** Логістичні реєстри замовлень (очищені CSV-експорти)
* **Мова запитів:** GoogleSQL (BigQuery SQL)
* **Моделювання:** dbdiagram.io (3NF / Star Schema)

## 📐 Етап 1: Проєктування та Нормалізація (1NF, 2NF, 3NF)

Сирі дані за серпень (`stg_raw_august`) містили серйозні аномалії: дублікати, пусті рядки, текстові назви замість ідентифікаторів, а також нетипізовані фінансові метрики (знаки валют `€` та пробіли в текстових полях) і дати в європейському текстовому форматі (`ДД.ММ.РРРР`).

Для уникнення аномалій модифікації, оптимізації аналітичних запитів та побудови коректного часового аналізу, дані були приведені до стану **Третьої нормальної форми (3NF)** і розподілені на зіркоподібну схему:

* **Таблиця фактів (`fct_orders`):** містить транзакційні дані замовлень, унікальні числові бізнес-метрики (`price_eur`, `distance_km`), три ключові дати для аналізу повного життєвого циклу доставки (`order_date`, `unloading_date`, `invoice_date`) та зовнішні ключі (FK) для зв'язку з вимірами.
* **Таблиці вимірів (Довідники / Dimensions):**
  * `dim_managers` — інформація про менеджерів (логістів), які супроводжують рейси.
  * `dim_trucks` — державні реєстраційні номери автомобілів.
  * `dim_geography` — унікальні адреси та коди точок завантажень/розвантажень (запобігає транзитивним залежностям адрес).

## 🔍 Етап 2: Очищення, Типізація та Data Quality

У процесі ETL/ELT дані пройшли повне технічне очищення:
1. **Фінансовий аудит:** Текстові рядки виду `"€1 150,00"` очищено від префіксів валют, нерозривних пробілів та приведені до системного числового типу `FLOAT64`.
2. **Часовий аналіз:** Текстові дати з крапками переформатовані у міжнародний стандарт баз даних `YYYY-MM-DD` (`DATE`), що дозволило використовувати аналітичні функції часового зрізу (наприклад, `DATE_TRUNC`).
3. **Цілісність:** Проведено технічний аудит зв'язків. Після фільтрації сміттєвих Excel-рядків зафіксовано 94 очищених замовлення від клієнтів з нульовим показником "завислих" або нетипізованих записів. Дані повністю цілісні й готові до побудови бізнес-метрик (наприклад, потижневої динаміки виручки).

## 📐 Схема даних (Database Schema)

![schema](schema.png)

```sql
-- ==========================================
-- 📐 СХЕМА ДАНИХ (DATABASE SCHEMA)
-- Побудовано за правилами 3NF (Зіркова схема)
-- ==========================================

-- 1. Створення довідника географії
CREATE OR REPLACE TABLE `pet-project-ymailo.pet_project.dim_geography` (
  geography_id INT64,
  full_address STRING
);

-- 2. Створення довідника менеджерів
CREATE OR REPLACE TABLE `pet-project-ymailo.pet_project.dim_managers` (
  manager_id INT64,
  manager_name STRING
);

-- 3. Створення довідника автомобілів (Траків)
CREATE OR REPLACE TABLE `pet-project-ymailo.pet_project.dim_trucks` (
  truck_id INT64,
  truck_number STRING
);

-- 4. Створення фінальної таблиці фактів замовлень
CREATE OR REPLACE TABLE `pet-project-ymailo.pet_project.fct_orders` (
  internal_order_id INT64,
  loading_geography_id INT64,
  unloading_geography_id INT64,
  manager_id INT64,
  truck_id INT64,
  price_eur FLOAT64,
  distance_km INT64,
  order_date DATE,
  unloading_date DATE,
  invoice_date DATE
);
```
